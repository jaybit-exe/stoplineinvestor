# Stopline /news: plan

Status: PREVIEW ONLY. Nothing here is deployed, pushed or live. The original repo (`/workspace/github_prep/stoplineinvestor`) is untouched; the preview is a copy in `/workspace/stopline_news/preview`.

## Goal and scope
A narrow news section on prop-firm and trading-risk news, not general market headlines. Four beats: **rule changes** (drawdown, consistency, contract limits), **payout and drawdown policy updates**, **closures, bans and restrictions**, **promos** (phase 2). Every item links to the calculator or firm preset that shows what the change means for a trader's account. Plus one **weekly economic calendar** for ES, NQ and BTC with sizing guidance that links to the position size calculator.

Why narrow: Stopline can't beat Reuters or CNBC on headlines, and thin aggregated content can hurt the calculator pages that already work. Prop-firm rule news with the "what it means for your numbers" part is something the calculators make Stopline uniquely able to do.

## URL structure
| URL | What |
|---|---|
| `/news/` | Index: calendar banner, latest posts, "how we cover news" |
| `/news/<slug>/` | One post. Slug = firm + the change, e.g. `topstep-restricts-new-accounts-13-countries` |
| `/news/calendar/` | The current week's economic calendar (always the live week) |
| `/news/calendar/YYYY-MM-DD/` | Phase 2: archive snapshot of a past week, created each Monday by moving last week's page here |
| `/news/feed.xml` | RSS 2.0 |
| `/news/<category>/` | Phase 2, once there are ~8 posts per category: `rule-changes`, `payouts`, `closures`, `promos` |

Lowercase, hyphenated, trailing slash, no dates in post URLs (so a post can be updated without a URL change). Fits the site's existing `html_handling: auto-trailing-slash` setup; no Worker change needed because `/news/*` is served as static assets (only `/api/*` runs the Worker first).

## Post template
Each post is one `section.card.prose` in the same layout as the guides:
1. Breadcrumb (News / Firm), H1, meta row: category tag, Published, Checked dates.
2. **Checked box** (the same `.checked` callout the guides use): when it was published, what it was checked against, link to the firm's page, "Stopline is not affiliated with <firm>", and whether the firm has a calculator preset.
3. **What changed**: plain-English summary and a before/after table with the firm's own numbers. Effective date and who is affected (new accounts only? existing too?).
4. **What it means for your numbers**: our own arithmetic or example, then 2 to 4 calculator links (preset link when the firm has one: `?p=<preset-id>`, otherwise Custom values in the query string).
5. **Sources**: firm page first (labelled "Official, primary"), then any report that adds context (labelled with what it adds).
6. Correction line pointing to `/contact/`.

Template and builder: `build.py` + `content.py` (one dict per post) + `news.css`. Adding a post = add a dict, run `python3 build.py`. News pages load a separate `news.css`; `style.css` and `app.js` are not changed.

## Schema (JSON-LD)
- **Posts: `NewsArticle`** with `headline`, `description`, `datePublished`, `dateModified`, `author` (Organization Stopline), `publisher` (Organization with logo), `image`, `mainEntityOfPage`, `about` (the firm), `articleSection` (category) and `citation` (the source URLs). Plus `BreadcrumbList`.
- **Calendar: `Article`** (it's a weekly explainer, not breaking news) with an `ItemList` of that week's events and a `BreadcrumbList`.
- **Index: `CollectionPage`** + `ItemList` + `BreadcrumbList`.
- The site's guides use `Article`; keep that for evergreen pages, use `NewsArticle` only for dated news. Always bump `dateModified` when a post changes and show the same date on the page (schema and visible dates must match).
- Don't mark up promo codes as `Offer` unless we're willing to keep the price and expiry current.

## Sitemap, RSS and discovery
- **Sitemap:** add `/news/`, `/news/calendar/` and every post with a real `lastmod`. The preview adds these to `site/sitemap.xml`. Since `robots.txt` already points at the sitemap, nothing else is needed. The Playwright smoke test in `tests/test.py` reads the sitemap, so new pages are tested automatically.
- **RSS:** `/news/feed.xml` (RSS 2.0, full title + summary, `atom:link` self, `guid` = permalink). Every news page has `<link rel="alternate" type="application/rss+xml">`. Generated by `build.py`.
- **Google News sitemap:** skip. It needs publisher approval and the content is niche; regular sitemap + RSS is enough.
- Add "News" to the nav (done in the preview on all 31 pages, plus a footer link) and a "Related news" link from each firm's rules guide when that firm has a new post.

## Update cadence
| What | When |
|---|---|
| Firm-news posts | As news breaks, verified same day. Target 2 to 3 a week; fewer is fine. Zero is better than unverified. |
| Weekly calendar | Publish **Sunday evening ET** for the coming week; re-check release times Monday 8 AM; archive Friday after the close. |
| Monthly roundup | First business day: one page listing every change that month by firm, linking to the posts. Good evergreen search target. |
| Re-check pass | Every Friday: re-open the source of each post from the last 14 days. If the firm changed it again, update the post, bump `dateModified`, add a visible "Updated" note. |
| Staleness | Posts older than 90 days with an out-of-date rule get a "Superseded" banner linking to the current guide, not deleted. |

Realistic effort: about 20 to 40 minutes per post and about 30 minutes for the weekly calendar if done by hand. A script can pull the release dates from the BEA/BLS/Fed pages to draft the calendar, but a human checks them.

## Sourcing rules (non-negotiable)
1. **Firm first.** Cite the firm's own help center, announcement, terms page or official post. Say when we read it.
2. **Two-source rule for anything damaging.** Closures, bans, withheld payouts or fraud claims need the firm's own notice, or two independent credible reports. Use "per the firm's notice" and quote it; never repeat allegations as fact. Don't name individuals.
3. **No copying.** Don't copy text from other sites, trackers or newsletters. Facts are free; wording is not. Link to them as "also reported by".
4. **No thin AI-rewritten content.** No post without Stopline's own value: a before/after table from the firm's numbers, our own arithmetic, and a calculator link. Never publish a rewrite of someone else's article or auto-generated summaries.
5. **If it can't be verified, leave it out.** No rumors, no "traders are saying", no screenshots without the firm's page.
6. **Dates and numbers:** every number traces to a source line. Convert times to ET. State effective dates and who is affected.
7. **Promos:** the firm's own page only, with the expiry date. Flag any affiliate link as `rel="sponsored"` and add an on-page disclosure (see risks). Never rank firms on promo size.
8. **Corrections** are public: fix the page and add a dated note.
9. **No advice:** state what changed and what the math is. Never "buy this account".

## Phased growth path
1. **Phase 1: News + calendar (this preview).** `/news/`, posts, weekly calendar, RSS, sitemap. Goal: 8 to 12 solid posts and 4 weekly calendars before judging. Success signals: indexed pages, return visits, clicks from posts into calculators.
2. **Phase 2: Calendar upgrades.** Archive snapshots, an "events that usually move ES/NQ/BTC" reference page, a downloadable `.ics`, "Add to calendar", a position-size link that pre-fills (needs a small `app.js` change so `/position-size/` accepts query params, which it doesn't today). Category pages and a monthly roundup.
3. **Phase 3: Delayed charts.** Free delayed charts for ES/NQ/BTC and the index ETFs via an embeddable widget (TradingView's free widgets are already used for the ticker). Don't build a data feed. Use delayed data with attribution. Put key levels and event markers on the weekly calendar.
4. **Phase 4: More.** Firm-change tracker table (a "what changed" page per firm that links to posts), email digest (needs an email provider, a privacy-page update and consent), and promos page once disclosure and affiliate rules are in place.
Each phase only starts if the previous one shows traffic and the update workload is sustainable.

## Risks and mitigations
| Risk | Mitigation |
|---|---|
| **Accuracy and liability.** A wrong rule or date can cost a trader money. | Firm-first sourcing, "checked" dates on every post, visible corrections, "confirm on the firm's page" in every checked box. |
| **Defamation** on closures, bans or fraud. | Quote the firm's notice, use "per the firm", two-source rule, no allegations, no named individuals. |
| **Thin or scaled content** (Google's spam policies) and dilution of the working calculator pages. | Low volume, own analysis in every post, calculator links, `noindex` for any tag or archive page with little content. Monitor Search Console for the calculator pages after launch. |
| **Maintenance burden.** Stale posts mislead and hurt trust. | Friday re-check pass, "Superseded" banners, small cadence. Stop at 1 post/week if time is short. |
| **Calendar errors** (times, holiday hours). | Each row cites its publisher; weekly re-check; holiday hours flagged as "confirm with CME". Show "checked" date. |
| **Affiliate/promo conflicts** (FTC disclosure). | Phase 2+ only; `rel="sponsored"`; on-page disclosure; keep news and promos on separate pages. |
| **Copyright** | No copied text, short quotes only with attribution, no logos or images from firms. |
| **Firm backlash or ToS** | State "not affiliated"; no scraping of firm sites; no use of firm logos. |
| **Preset coverage.** Only 6 firms have presets; most news is about other firms. | Custom-value links (as in the FTMO and Blue Guardian samples); add presets for the next most-searched firms (FTMO Futures, Blue Guardian) as separate, verified work. |
| **Site changes outside the news folder.** | Phase 1 only adds the nav + footer link to existing pages; no JS, CSS or Worker changes. `news.css` is separate. |

2. In a **branch** of `jaybit-exe/stoplineinvestor`, copy in: `site/news/`, `site/assets/news.css`, the updated `site/sitemap.xml`, and the 31 nav/footer-patched pages. Don't run a bare `wrangler deploy` against that config. Use the real config (or `--name cold-poetry-d8dc` with the account id set) so it updates the existing Worker, not a new one.
5. After deploy: submit `/news/` and the new sitemap in Search Console, check `/news/feed.xml` loads with an XML content type, check Cloudflare cache purge if needed.
6. For each later post: add a dict to `content.py`, run `build.py`, copy the changed files, run the tests, deploy.
